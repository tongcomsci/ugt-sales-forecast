## 🔒 ความปลอดภัย (4 ข้อ)

### 1. เอารหัสผ่านฐานข้อมูลออกจากโค้ด

**ปัญหา:** ไฟล์ที่ดึงข้อมูล Inventory มีรหัสผ่านฐานข้อมูล `UBE_DW` เขียนไว้ตรงๆ ในโค้ด (ครบทั้งชื่อเซิร์ฟเวอร์ ผู้ใช้ รหัสผ่าน) และอยู่ในประวัติ git มาตั้งแต่ commit แรกที่ทำ backend ตรวจแล้วว่า**ไม่ได้ตั้งค่าไว้ที่อื่นเลย** แปลว่าระบบใช้รหัสในโค้ดอยู่จริง

**วิธีแก้:** เปลี่ยนไปอ่านข้อมูล Inventory ผ่าน **linked server `THRYGSD002`** บน connection หลัก ซึ่งใช้ `sa` อยู่แล้วและเข้าถึงได้ทุก database — **ตัด database connection ตัวที่สองทิ้งทั้งก้อน**

ผลคือไม่มีรหัสผ่านชุดที่สองให้ต้องดูแลอีก (ตอนแรกวางแผนจะย้ายไปไฟล์ตั้งค่า แต่วิธีนี้ดีกว่าเพราะไม่เหลืออะไรให้ดูแล)

📍 `src/api/routes/inventory.ts` — ลดจาก 36 เหลือ 15 บรรทัดในส่วนนี้

### 2. ให้สิทธิ์ admin จากรหัสพนักงาน ไม่ใช่ชื่อ

**ปัญหา:** ระบบเช็คว่าเป็น admin ไหมจาก **ชื่อ-นามสกุลที่แสดง** และร้ายกว่านั้นคือมันเชื่อชื่อที่ Keycloak ส่งมาโดยไม่ตรวจกับ HR เลย — ใครก็ตามที่ตั้งชื่อแสดงผลตรงกับ 1 ใน 3 ชื่อที่กำหนดไว้ จะได้สิทธิ์ admin ทันที **โดยไม่ต้องมีตัวตนใน HR ด้วยซ้ำ**

**วิธีแก้:** เปลี่ยนไปเทียบ **รหัสพนักงาน** ซึ่งไม่ซ้ำและมาจากระบบ HR (91207, 91008, 91226) และคนที่ไม่มีตัวตนใน HR เป็น seed admin ไม่ได้อีก แก้ครบทั้ง 3 จุดที่เคยเทียบชื่อ

**หมายเหตุ:** ตรวจแล้วว่าตอนนี้ยังไม่มีชื่อซ้ำในระบบ HR — เป็นความเสี่ยงที่ยังไม่ถูกใช้ ไม่ใช่ความเสียหายที่เกิดแล้ว

📍 `src/api/services/appRoles.ts`

### 3. ทำให้ session หมดอายุจริง

**ปัญหา:** ระบบจำ session ไว้ในหน่วยความจำแต่**ไม่เคยกำหนดวันหมดอายุฝั่งเซิร์ฟเวอร์** จะลบก็ต่อเมื่อกดปุ่ม logout เท่านั้น

ที่เข้าใจผิดกันคือ cookie มีตั้ง "หมดอายุ 8 ชั่วโมง" ไว้ — แต่นั่น **browser เป็นคนบังคับ ไม่ใช่เซิร์ฟเวอร์** ถ้าใครคัดลอกค่า cookie ออกไปได้ จะใช้เข้าระบบได้**ตลอดไป**

**วิธีแก้:** เก็บวันหมดอายุไว้ฝั่งเซิร์ฟเวอร์ อ่าน session ทุกครั้งผ่านฟังก์ชันที่เตะของหมดอายุทิ้ง และให้ cookie ใช้ค่าอายุตัวเดียวกับที่เซิร์ฟเวอร์บังคับ (เดิมเขียนเลขซ้ำ 2 ที่ ซึ่งวันหนึ่งจะเพี้ยนกัน)

พร้อมกันนี้เพิ่มการกวาดข้อมูลชั่วคราวของ login ที่เริ่มแล้วไม่จบ — เดิมล้างเฉพาะเมื่อ login สำเร็จ ใครก็ยิงหน้า login ซ้ำๆ ให้หน่วยความจำโตได้โดยไม่ต้องมีสิทธิ์อะไร

📍 `src/api/auth.ts`

## 📊 ความถูกต้องของข้อมูล (4 ข้อ)

### 5. แยกข้อมูลรายเดือนกับรายสัปดาห์ไม่ให้ทับกัน

**ปัญหา:** ระบบเก็บ forecast ได้ทั้งรายเดือนและรายสัปดาห์ แต่ตอนบันทึก**ไม่ได้แยกว่าแถวนี้เป็นแบบไหน** ใช้แค่ (ลูกค้า + เวอร์ชัน + วันที่) เป็นตัวระบุ

ข้อมูลรายเดือนเก็บเป็นวันที่ 1 ส่วนรายสัปดาห์เก็บเป็นวันพุธแรกของเดือน — **บางเดือนวันที่ 1 เป็นวันพุธพอดี** ตัวระบุจะซ้ำกันเป๊ะ แล้วคำสั่งบันทึกจะเขียนทับ **พร้อมเปลี่ยนประเภทของแถวเดิมไปเลย** ข้อมูลจะหายจากหน้าจอโดยไม่มี error

**ตรวจข้อมูลจริงก่อนแก้:**

| รายการ | ผล |
|---|---|
| แถวรายสัปดาห์ที่ตกวันที่ 1 | 2,928 แถว (เม.ย. และ ก.ค. 2026) |
| ในจำนวนนั้น มีลูกค้าที่มีข้อมูลรายเดือนด้วย | **0 ราย** |

แปลว่า**ยังไม่มีข้อมูลไหนหายไป** ลูกค้าที่ใช้โหมดสัปดาห์กับโหมดเดือนเป็นคนละกลุ่มกันสนิท — เป็นระเบิดเวลาที่ยังไม่ระเบิด

**วิธีแก้:** เพิ่ม `granularity` เข้าไปในตัวระบุแถว (primary key) และแก้คำสั่งบันทึกทั้ง 3 จุดให้เทียบ `granularity` ด้วย

ทำตอนนี้ง่ายเพราะข้อมูลยังไม่เสียหาย — การขยาย key ไม่มีทางสร้างข้อมูลซ้ำ จึงไม่ต้องล้างข้อมูลก่อน migration ใช้เวลารัน 5.7 วินาที ข้อมูลครบ 44,856 แถวเหมือนเดิม

📍 `prisma/schema.prisma` · migration `20260908120000_forecast_values_granularity_in_pk`

**วิธีแก้:** เมื่อเจอชื่อสูตรที่ยังไม่ผูก ระบบใช้ราคาที่อัปโหลด/คีย์เท่านั้น ถ้ายังไม่มีราคาจะเว้นเป็น 0 ให้เห็นชัดว่าต้องกรอก — ไม่คำนวณทับให้อีก

### 13. ไม่ให้ระบบแก้วันที่เงียบๆ

**ปัญหา:** พบ 2 อย่าง อย่างที่สองหนักกว่าที่คาด

```
ใส่ 2026-01-15 แบบรายเดือน  →  กลายเป็น 2026-01-01 เงียบๆ
ใส่ค่าขยะเช่น "hello"        →  คืนค่าวันที่ใช้ไม่ได้ (Invalid Date) เงียบๆ
```

เงื่อนไขในโค้ดทำให้การตรวจรูปแบบถูกลัดผ่าน ค่าขยะจึงไม่เคยไปถึงจุดที่ควรแจ้ง error

**วิธีแก้:** ยังรับ `YYYY-MM` และ `YYYY-MM-01` (2 รูปแบบที่ระบบ import สร้างจริง) นอกนั้นแจ้ง error และวันที่ที่เป็นไปไม่ได้ถูกปฏิเสธแทนที่จะคืนค่าใช้ไม่ได้

### 15. สร้างชุดทดสอบอัตโนมัติ

**ปัญหา:** ทั้งโปรเจค (โค้ดประมาณ 34,000 บรรทัด) มีไฟล์ตรวจสอบอัตโนมัติแค่ **1 ไฟล์** และพบว่า `Jenkinsfile` **ไม่ได้เรียกมันเลย** ทั้งที่คู่มือโปรเจคเขียนว่า CI รัน — CI มี 7 stage แต่รันแค่ `lint` กับ `build`

## 🔴 เหลือ 1 ข้อ — ต้องทีมอื่นทำ

### ใบรับรองความปลอดภัย (cert) ใกล้หมดอายุ

```
cert *.ube.co.th  หมดอายุ 4 ตุลาคม 2026
```

**ถ้าไม่ต่ออายุ:** เบราว์เซอร์ของผู้ใช้จะบล็อกเว็บทั้งหมด ไม่ใช่แค่หน้า login เพราะแอปทั้งตัวเสิร์ฟจากโดเมนนี้ — **ทั้งบริษัทใช้ระบบไม่ได้**

**จุดที่อันตราย:** ในไฟล์ตั้งค่ามี `NODE_TLS_REJECT_UNAUTHORIZED=0` ซึ่งปิดการตรวจใบรับรองทั้งเซิร์ฟเวอร์ ทำให้**ฝั่งเซิร์ฟเวอร์ยังทำงานได้ปกติแม้ cert หมดอายุ** — log จะเงียบสนิท ไม่มีสัญญาณเตือนล่วงหน้า จะรู้ตัวก็ตอนผู้ใช้โทรมาบอก

**ต้นเหตุที่ต้องมีบรรทัดนั้น (ตรวจพบจริง):** cert เป็น**ใบจริงที่ซื้อมา** ออกโดย RapidSSL ไม่ใช่ใบที่ออกเอง แต่ **nginx ตั้งค่าส่ง cert ไม่ครบสาย** ส่งแต่ใบปลายไม่ส่งใบกลาง เบราว์เซอร์หาใบกลางเองได้จึงไม่ฟ้อง แต่ Node ทำไม่ได้

พิสูจน์แล้วด้วยการโหลดใบกลางมาใส่แล้วทดสอบซ้ำแบบเปิดตรวจเต็มที่ → ผ่าน

**ต้องทำ 2 อย่าง**

| ลำดับ | สิ่งที่ต้องทำ | ใคร |
|---|---|---|
| 1 | ต่ออายุ cert `*.ube.co.th` | ทีมที่ดูแลโดเมน |
| 2 | แก้ nginx ให้ส่ง cert ครบสาย (fullchain) แล้วลบ `NODE_TLS_REJECT_UNAUTHORIZED=0` | ทีม IT |

ทำข้อ 2 พร้อมข้อ 1 ได้ในทีเดียว
