### 2. ✅ ฐานข้อมูลจริงกับไฟล์ migration ไม่ตรงกัน (schema drift)

> 🔴 **แก้ไขจากรายงานฉบับแรก — ข้อนี้เขียนผิดทั้งข้อ**
> ฉบับแรกผมเขียนว่า "สูตร `FactForecast` ตกรุ่น ไม่สนใจราคาที่ import, spread ที่เป็นข้อความทำ query ล้ม, ดึงจากตารางเก่า" — **ผิดทั้งหมด** เพราะผมอ่านจากไฟล์ migration ใน repo แต่ **view ตัวจริงในฐานข้อมูลไม่ใช่ตัวนั้น** เมื่อดึงนิยามจริงจาก `sys.sql_modules` มาดู พบว่าเป็น view คนละตัวกันเลย และทำงานถูกต้องกว่าที่ไฟล์ระบุ

**สิ่งที่เจอจริง**

| | view ตัวจริงในฐานข้อมูล | ไฟล์ migration ล่าสุดใน repo |
|---|---|---|
| จำนวนบรรทัด | **444** | 108 |
| อ่านข้อมูลจาก | `forecast_change_logs` (ประวัติการแก้ไข) | `forecast_values` (ค่าปัจจุบัน) |
| ราคา / ยอดเงิน | ใช้ `newPriceFcst` / `newAmountFcst` ที่เก็บไว้ | คำนวณ `CPL + spread` เอง |
| `cpl_prices` | ไม่ใช้ | ใช้ |
| `effectivePrice` / `spread` | **ไม่มีเลย** | มี 5 จุด |
| แยก `granularity` | **ใช่** | ไม่ |

**แปลว่าอะไร**
มีคนแก้ view ตัวนี้**ตรงในฐานข้อมูล** โดยไม่ได้ทำเป็น migration ทำให้ไฟล์ใน repo ไม่ตรงกับของจริงอีกต่อไป

**ข่าวดี:** view ตัวจริงทำงาน**ดีกว่า**ที่ไฟล์ระบุ — มันใช้ราคาที่เก็บไว้จริง แยก granularity ถูกต้อง และไม่แตะ spread เลย จึงไม่มีปัญหา error จาก spread ที่เป็นข้อความอย่างที่ผมกลัวไว้

**ข่าวร้าย — และนี่คือปัญหาจริงของข้อนี้:**

| ความเสี่ยง | ผลที่ตามมา |
|---|---|
| ถ้าสร้างฐานข้อมูลใหม่จาก migration | จะได้ view ตัวเก่า 108 บรรทัดที่คำนวณราคาผิด → ตัวเลข Power BI เพี้ยนทันที |
| Docker รัน `prisma migrate deploy` ตอน start | ถ้ามีใครเพิ่ม migration ที่ recreate view นี้ จะ**ทับของจริงทิ้ง** |
| คนอ่าน repo ไม่มีทางรู้ว่า Power BI อ่านอะไรจริง | review โค้ดไม่ได้ แก้ต่อไม่ได้ ไม่รู้ว่าใครแก้อะไรไปเมื่อไหร่ |

**ต้องทำอะไร**
1. ดึงนิยาม view ตัวจริงจาก `sys.sql_modules` ออกมา แล้วทำเป็น migration ใหม่ให้ repo ตรงกับของจริง
2. ตรวจ `DimRegistration` แบบเดียวกัน (ตัวจริง 123 บรรทัด — ยังไม่ได้เทียบละเอียด)
3. ตกลงกันในทีมว่า **ห้ามแก้ view ตรงในฐานข้อมูล** ต้องผ่าน migration เท่านั้น

**ดึงนิยามจริงออกมาดูได้ด้วย**
```sql

```

## 🔴 เรื่องที่พบเพิ่ม หลังตรวจรอบสอง (2 เรื่อง)

### 14. ระบบปิดการตรวจใบรับรองความปลอดภัยทั้งเซิร์ฟเวอร์

**เกิดอะไรขึ้น**
ในไฟล์ตั้งค่ามีบรรทัด `NODE_TLS_REJECT_UNAUTHORIZED=0`

ค่านี้สั่งให้ Node.js **เลิกตรวจใบรับรอง (certificate) ของทุกการเชื่อมต่อ HTTPS ที่ยิงออกจากเซิร์ฟเวอร์** ไม่ใช่แค่ตัวที่มีปัญหา — รวมถึงขั้นตอน**แลก token กับ Keycloak ตอน login** และการส่งอีเมล

**ทำไมถึงเป็นปัญหา**
ถ้ามีใครดักกลางทางได้ เขาสามารถปลอมใบรับรองเป็น Keycloak แล้วขอ token ของผู้ใช้ไปได้ โดยเซิร์ฟเวอร์จะไม่ทักท้วงอะไรเลย เพราะถูกสั่งไม่ให้ตรวจ

**สาเหตุจริง — ไม่ใช่ cert ภายในบริษัทอย่างที่คิดตอนแรก**

ดึงใบรับรองของ `ugtweb.ube.co.th` มาดูตรงๆ พบว่า:

```
subject : *.ube.co.th
issuer  : RapidSSL TLS RSA CA G1     <- CA เชิงพาณิชย์ ที่ทุกระบบเชื่อถืออยู่แล้ว
chain   : จบที่ชั้น 0 - ไม่ส่งใบกลาง (intermediate) มาด้วย
ใช้ได้ถึง: 4 ตุลาคม 2026
```

cert เป็น**ใบจริงที่ซื้อมา** ไม่ใช่ใบที่ออกเอง ปัญหาคือ **nginx ตั้งค่าส่ง cert ไม่ครบสาย** ส่งแต่ใบปลายไม่ส่งใบกลาง เบราว์เซอร์มักหาใบกลางเองได้จึงไม่ฟ้อง แต่ Node ทำไม่ได้

**พิสูจน์แล้ว:** โหลดใบกลางของ RapidSSL มาใส่ `NODE_EXTRA_CA_CERTS` แล้วเชื่อมต่อแบบเปิดตรวจ cert เต็มที่ → ผ่าน HTTP 200 ยืนยันว่านี่คือต้นเหตุเดียว

**ถ้าลบบรรทัดนี้ทิ้งเฉยๆ login จะพังทันที** จึงยังไม่ได้แก้ให้

**วิธีแก้ — 2 ทาง**

| ทาง | วิธีทำ | ข้อดี |
|---|---|---|
| **แก้ที่ nginx** (ดีที่สุด) | เปลี่ยน `ssl_certificate` ให้ชี้ไฟล์ fullchain (ใบปลาย + ใบกลางต่อกัน) แล้วลบ flag นี้ได้เลย | แก้ครั้งเดียว จบทุก client ไม่ใช่แค่แอปนี้ |
| **แก้ฝั่งแอป** (เร็ว ไม่ต้องพึ่งใคร) | โหลด `https://cacerts.digicert.com/RapidSSLTLSRSACAG1.crt.pem` เก็บไว้ในโปรเจค แล้วตั้ง `NODE_EXTRA_CA_CERTS` ชี้ไปที่ไฟล์นั้น | ใบกลางเป็นไฟล์สาธารณะ ไม่ต้องขอจาก IT |

> ⚠️ **เรื่องด่วนกว่า:** cert หมดอายุ **4 ต.ค. 2026** (อีก 26 วันจากวันที่ตรวจ) ถ้าไม่ต่ออายุ ระบบจะ login ไม่ได้ทั้งหมด และเพราะ flag นี้เปิดอยู่ ระบบจะไม่เตือนอะไรจนกว่าจะพังจริง จังหวะต่ออายุคือจังหวะที่เหมาะจะแก้ chain ให้ถูกไปพร้อมกัน

### 7. ✅ ออกจากระบบแล้ว แต่ session ยังไม่ตาย

**เกิดอะไรขึ้น**
ตอน login ระบบจะจำ session ไว้ในหน่วยความจำ แต่**ไม่เคยกำหนดวันหมดอายุฝั่งเซิร์ฟเวอร์เลย** จะลบก็ต่อเมื่อผู้ใช้กดปุ่ม logout เท่านั้น

ที่หลายคนเข้าใจผิดคือ ตัว cookie มีตั้ง "หมดอายุใน 8 ชั่วโมง" ไว้ — แต่อันนั้น **browser เป็นคนบังคับ ไม่ใช่เซิร์ฟเวอร์** ถ้าใครก็ตามคัดลอกค่า cookie ออกไปได้ จะใช้เข้าระบบได้**ตลอดไป** แม้จะเกิน 8 ชั่วโมงไปนานแค่ไหนก็ตาม

อีกจุดหนึ่ง: ข้อมูลชั่วคราวตอนกำลัง login จะถูกล้างเฉพาะเมื่อ login **สำเร็จ** ถ้ามีคนยิงหน้า login ซ้ำๆ โดยไม่ login จริง หน่วยความจำจะโตขึ้นเรื่อยๆ โดยไม่ต้องมีสิทธิ์อะไรเลย

> ไฟล์ migration **ไม่ใช่**แหล่งข้อมูลที่เชื่อถือได้ว่าฐานข้อมูลจริงเป็นอย่างไร ข้อ 2 ผมสรุปผิดเพราะอ่านจากไฟล์ ครั้งต่อไปที่จะวิเคราะห์ view หรือ stored procedure ต้องดึงจาก `sys.sql_modules` มาดูก่อนทุกครั้ง

**สิ่งที่รายงานนี้ยังไม่ครอบคลุม**
- ไม่ได้เทียบ `DimRegistration` ตัวจริง (123 บรรทัด) กับไฟล์ migration อย่างละเอียด — น่าจะ drift เหมือนกัน
- ไม่ได้ตรวจว่ามี view / stored procedure อื่นที่ drift อีกไหม
- ไม่ได้ทดสอบ UI ด้วยมือ หรือทดสอบ import ไฟล์ Excel จริง
- ไม่ได้ตรวจเรื่อง performance ภายใต้การใช้งานจริง
